# Аудит исходного проекта Slay Investments

Дата аудита: 2026-11-07

## 1. Зафиксированное состояние

Репозиторий содержит небольшой автономный прототип без менеджера пакетов и внешних runtime-зависимостей:

- `server.py` — Python backend на `http.server`, `ThreadingHTTPServer` и встроенном `sqlite3`.
- `web/index.html` — HTML-точка входа.
- `web/app.js` — vanilla JavaScript: рендер экранов, SVG-график, вызовы API и состояние браузера.
- `web/styles.css` — единый CSS-файл интерфейса и media queries.
- `data/rounds.json` — пять подготовленных сценариев (`SBER`, `GAZP`, `NVTK`, `TATN`, `LKOH`), в каждом по 90 наблюдений: 60 до решения и 30 после.
- `scripts/fetch_data.py` — загрузка дневных закрытий с MOEX ISS для подготовки локального датасета.
- `.gitlab-ci.yml` — этап `build` с `py_compile` и проверкой JSON, этап `test` с проверкой обязательных полей.

Точки запуска:

- backend: `python server.py`, по умолчанию порт `8000`, переопределяется `PORT`;
- frontend: статические файлы из `web/`, `/` переписывается на `index.html`.

## 2. Реализованные маршруты и поток данных

- `POST /api/session` создаёт UUID-сессию, фиксированный порядок пяти сценариев и строку времени в SQLite.
- `GET /api/session` читает `X-Session-Id`, отдаёт текущий публичный раунд и историю завершённых раундов.
- `POST /api/answer` принимает ответ текущего раунда, выполняет расчёт на сервере, записывает результат и увеличивает `round_index` условным SQL-update.
- Для уже завершённого индекса backend может вернуть ранее сохранённый результат, что частично защищает от повторного начисления.
- До ответа frontend получает только 60 нормализованных значений `chart`; будущие цены остаются в JSON на сервере.

SQLite создаётся лениво в `data/stockguessr.sqlite3`. Таблицы `sessions` и `answers` создаются через `CREATE TABLE IF NOT EXISTS`; миграций и версии схемы нет.

## 3. Игровая логика, которая уже работает

- Стартовый капитал `100000`, базовое распределение 50/50 описано в расчёте и UI.
- Стратегии `buy`, `hold`, `sell` преобразуются в доли акции 100%, 50% и 0%.
- Направление определяется сервером по порогам `+5%` и `-5%` за 30 наблюдений.
- Отдельно считаются угадывание тикера, периода и направления, стоимость выбранного портфеля и три альтернативы.
- После пяти индексов frontend показывает итоговую страницу с агрегатами по компании, периоду и прогнозу.

## 4. Найденные проблемы и ограничения

### Критичные для обязательного кейса

1. В сценарии нет образовательного мини-теста, факторов, структурированного разбора и подтверждения теста до раскрытия.
2. `public_round` передаёт список компаний с тикерами и названиями. Это не раскрывает правильную компанию, но допускает угадывание по ограниченному списку и не моделирует отдельный этап выбора контекста.
3. У публичного раунда нет серверного state machine: обязательные поля проверяются, но нет статусов `quiz_pending`, `ready_to_submit`, `revealed`.
4. Схема `answers.result` хранит весь результат одним JSON без версии, score-компонентов или идемпотентного ключа запроса.
5. Граница существенного изменения захардкожена в `calculate` и не вынесена в конфигурацию.
6. В результате возвращается `all_prices`, включая исходные цены и даты. Это допустимо только после ответа, но контракт явно не разделяет `public` и `reveal` payload.
7. Нет серверной проверки длины/типа года, диапазона текста кроме обрезания rationale при записи, и нет ограничения размера входного HTTP-тела.

### Продуктовые и UX-проблемы

1. Текущий интерфейс позиционируется как StockGuessr, хотя продукт по требованиям называется Slay Investments.
2. Дизайн использует синюю светлую тему и не соответствует целевой тёмной палитре.
3. График — статический SVG без hover-tooltip и без доступных аналитических слоёв.
4. На landing есть маркетинговый образец графика; на экране раунда отсутствуют пошаговое раскрытие, карточка «Что мы узнали» и микрообъяснения терминов.
5. Итоговая сумма складывает пять независимых портфелей, что может быть неверно понято как капитал одной последовательной сессии.
6. Нет явного состояния загрузки/ошибки отсутствующего проверенного датасета на уровне контракта данных.

### Инженерные проблемы

1. Backend, модели, расчёты и HTTP-обработчик находятся в одном файле.
2. Нет автоматизированных unit/integration тестов; CI проверяет только синтаксис и наличие полей.
3. `scripts/fetch_data.py` обращается к внешнему API, но не проверяет дубликаты торговых дней, пропуски, изменение схемы ответа и происхождение каждого поля.
4. Нет статуса публикации сценария и человеческого утверждения LLM-контента.
5. Нет CORS/CSRF-модели, rate limit и общего ограничения тела запроса. Для локального демо это не блокирует запуск, но требует явного решения перед публикацией.
6. В репозитории есть дублирующий `spirit-team/policy.yml`; конфигурация Git не меняется, файл оставлен без изменений.
7. В окружении аудита отсутствуют `python`, `node` и `npm`, поэтому локальный запуск и существующие CI-команды невозможно выполнить в этой сессии.

## 5. Что сохранить

- Локальный проверенный датасет MOEX и его ссылки на источники.
- Отдельный скрипт подготовки котировок, работающий только вне пользовательского раунда.
- SQLite и UUID-сессии как лёгкую основу для MVP.
- Серверное вычисление доходности и альтернативных стратегий.
- Vanilla frontend без тяжёлого bundler-стека; это снижает стоимость демонстрации.
- Существующие responsive media queries как основу для последующей визуальной переработки.

## 6. Что переработать

- Ввести нормализованный контракт сценария с `scenario_id`, `status`, `thresholds`, `quiz`, `factors`, `educational_summary` и `sources`.
- Вынести расчёты, валидацию, хранилище и API в логические модули, сохранив запуск одним `server.py`.
- Добавить серверное состояние раунда и отдельные public/reveal DTO.
- Добавить тесты на данные, нормализацию, расчёты, идемпотентность и запрет утечки будущего.
- Переработать UI в тёмную editorial fintech систему Slay Investments, добавить тест, раскрытие и образовательный разбор.
- Добавить интерфейс LLM-провайдера и offline fallback без вызова модели во время раунда.

## 7. Целевая архитектура

```text
data/rounds.json (approved scenarios)
        |
        v
server.py -> api.py -> sessions / rounds / scoring / portfolio / validation
                          |                         |
                          v                         v
                       SQLite                  public DTO / reveal DTO
                          |
                          v
                 web/app.js + design system CSS
```

Подготовка контента выполняется отдельно:

```text
MOEX ISS -> market_data preparation -> scenario draft
verified facts + optional LLM provider -> validator -> human approval -> approved dataset
```

LLM получает только проверенные факты и не имеет права изменять котировки, даты и идентификаторы. При недоступном API движок использует approved локальные сценарии.

## 8. Порядок реализации

1. Зафиксировать и валидировать новый контракт данных, добавить fallback и понятные ошибки.
2. Разделить серверные расчёты и ввести состояния раунда с идемпотентным завершением.
3. Добавить quiz, факторы, отдельные score-компоненты и образовательный разбор.
4. Обновить API и frontend-поток пяти раундов.
5. Переработать дизайн-систему, график, мобильную адаптацию и reduced-motion.
6. Добавить unit/integration тесты и CI-проверки.
7. Добавить LLM provider/validator и документацию.
8. Подготовить дополнительные механики после стабилизации MVP.

## 9. Технические риски

- Исторические данные могут быть недоступны во время подготовки; runtime не должен заменять их случайными котировками.
- MOEX может изменить формат ISS или ограничения доступа; нужен локальный approved snapshot.
- Реакцию рынка нельзя сводить к единственной причинной связи; тексты должны разделять факты и гипотезы.
- SQLite подходит для демонстрации, но для многопользовательского запуска потребуется отдельная БД и миграции.
- Без Python/Node в текущем окружении визуальная и интеграционная проверка должна выполняться в CI или на машине разработчика.

## 10. Статус после итерации Slay Investments (2026-11-07)

Этот раздел обновляет устаревшие пункты выше, которые описывали состояние до текущих изменений:

- Добавлены users/auth_tokens/login_attempts; пользовательская авторизация использует PBKDF2-SHA256, случайный bearer token в HttpOnly cookie, и ограничение неуспешного входа.
- Добавлены авторизованные API профиля, туториала, открытых уровней и серверная проверка доступа к игровым сессиям. Туториал сохраняет шаг и может быть перезапущен из профиля.
- Расширены HTTP integration checks: анонимный запуск отклоняется, перескок туториала отклоняется, Medium закрыт до полной Easy-сессии, а после пяти ответов профиль показывает завершённую сессию и ответы.
- UI переработан в общую Slay editorial систему; добавлены регистрация/вход, интерактивные шаги обучения, уровень сложности, профиль, сводка события и факторов, сохранение черновика раунда.
- `uv run --no-cache python -m unittest discover -s tests -v` проходит 7 тестов; Playwright Chromium проходит 2 браузерных сценария на desktop и mobile viewport. Подробности и снимки — в `docs/E2E_TEST_REPORT.md` и `artifacts/ui-audit/`.
- Учебная практика отделена от игровых ответов: до регистрации/авторизации endpoint закрыт, до фиксации отдаются только 60 точек, после ответа — разбор и 30 точек; завершить туториал без практики нельзя.
- Полный продуктовый набор не завершён: датасет содержит только пять сценариев, поэтому независимого набора из пяти случаев на каждый уровень нет; LLM-рекомендации отсутствуют. Для дальнейшего расширения нужны дополнительные проверенные сценарии и фактчекинг.
