# Целевая архитектура

## Runtime

Остаёмся на стандартной библиотеке Python и vanilla JS: это сохраняет воспроизводимый запуск хакатонного MVP без сборщика и внешних сервисов. Backend владеет сценариями, состояниями, расчётами и раскрытием.

## Аккаунты и прогрессия

`users` хранит публичный профиль, PBKDF2-хеш пароля, состояние туториала, флаг завершения учебной практики и открытый уровень. `auth_tokens` хранит случайные серверные токены с истечением срока; браузер получает токен через HttpOnly/SameSite cookie. `sessions.user_id` и `sessions.level` связывают игровую сессию с аккаунтом и проверяются на каждом защищённом чтении/записи. Добавление таблиц/колонок выполняется идемпотентно в `connect()` и сохраняет прежние игровые записи.

Пользовательские игровые API закрыты до регистрации и завершения туториала. Переходы tutorial step последовательны; последний шаг требует отдельный ответ на учебный сценарий. `/api/tutorial/practice` раскрывает 60 точек до ответа, а после валидного ответа возвращает следующие 30, не записывая учебный ответ в игровую статистику. После пяти сохранённых игровых ответов backend повышает открытый уровень Easy → Medium → Hard. Профиль вычисляется из сохранённых игровых ответов, не из клиентских счётчиков.

## Логические области

- **scenarios/data** — approved snapshot котировок, фактов и образовательного контента.
- **validation** — проверка структуры, статуса публикации, наличия 60 + 30 наблюдений и quiz.
- **sessions/rounds** — SQLite-сессия, порядок пяти раундов, текущий индекс и идемпотентность.
- **portfolio/scoring** — классификация изменения, расчёт трёх стратегий и раздельных метрик.
- **api** — public DTO до решения и reveal DTO после ответа.
- **llm** — будущий offline-preparation pipeline; игровой runtime от него не зависит.

## Защита будущего

`public_round()` отдаёт только нормированные первые 60 значений, факторы и quiz без правильных ответов. `calculate()` добавляет `reveal_prices`, фактическое направление и объяснения после успешной записи ответа. Повторный POST для уже закрытого индекса возвращает сохранённый результат без повторного INSERT.

## Состояния

`awaiting_decision` → запись ответа → следующий `awaiting_decision`; после пятого ответа — `completed`. SQL `BEGIN IMMEDIATE`, первичный ключ `(session_id, round_index)` и условное обновление `round_index` защищают от двойного завершения.

## Дальнейшая эволюция

При росте нагрузки SQLite можно заменить на PostgreSQL через repository interface. Логика расчётов и DTO должны остаться независимыми от HTTP и UI.
